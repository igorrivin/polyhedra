# Narrow real-schema adapter, revision v3

The accepted computation receipt uses `/accepted_author_result` with exactly `{path, sha256, bytes}`. Its path is `computation/full-v2/author-result-70-110.json`, an OUTER-relative file. Revision v2 correctly preserved the approval bytes but required only `{sha256, bytes}`, so it could not admit the real receipt. The change is confined to the approval identity adapter and an explicit template shape declaration. It does not widen scientific comparison, metadata exclusions, runtime/manuscript guards, input-graph validation, or receipt reservation rules.

The new shape is `path-record`; the omitted/default shape remains `identity`. Both require exact key sets and a lowercase SHA-256 string plus a nonnegative integer byte count (Boolean and float values fail). The path-bearing shape also requires a canonical relative non-sidecar path inside OUTER and equality with the declared reference path, including resolved equality. An absolute approved path, traversal, spelling normalization, or a different reference is rejected even if the content identity happens to match. The projection occurs only after these checks. The final reference file is still independently snapshotted and compared with both the pinned specification identity and the projected approved identity.

Five new tests cover the adapter's positive/default paths, key/type/shape rejection, unsafe or mismatched paths, full synthetic replay plus comparison admission using the actual approval shape, and altered-path failure before launch or comparison with serialized failure receipts. All previous fifty gate tests remain. Synthetic source commits and reports are test fixtures, not scientific or review success evidence.

The real-schema observation records the actual computational receipt and reference identities using this adapter. It is a read-only compatibility check, not final approval binding or a clean-source replay. The unready templates retain unresolved source, integration/PDF, and lifecycle fields; their illustrative pointers must be bound from actual receipts in the separate binding plan.

Verification records are under `verification-v3/`. Independent targeted recheck is required before this revision is used for the real checkpoint. No canonical edits, real science/PDF execution, Git staging/commit, evidence transfer or upload was performed here.
